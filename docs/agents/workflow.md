# Порядок работы

Как идёт работа над проектом от сессии к сессии. Коротко то же самое есть в `CLAUDE.md` («Порядок работы»), здесь подробности.

## Путь каждой части работы

Часть работы — кусок дорожной карты (`PROJECT_CONTEXT.md`, раздел 3) или его логичная доля, проблема или правка. Как делить, решает агент; деление предлагается в описании и подтверждается владельцем.

| Шаг | Файл | Что в нём |
|---|---|---|
| 1. Описание | `.scratch/<часть>/description.md` | Что сделать и зачем, простыми словами: цель, что увидит владелец, что не входит, открытые вопросы |
| 2. Спека | `.scratch/<часть>/spec.md` | Точное поведение, крайние случаи, что и как проверяется. Пишется по описанию |
| 3. Тикеты | `.scratch/<часть>/issues/NN-<slug>.md` | По тикету на законченный кусок, который можно проверить сам по себе; нумерация с `01` |
| 4. Тикеты по одному | код, тесты, документация | Один тикет за сессию |
| 5. Код-ревью | `.scratch/<часть>/review.md` | Ревью всей части после последнего тикета: сверка со спекой и `docs/coding-standards.md` (скил `code-review`) |

Каждая находка ревью получает решение в `review.md`: **чинить** — становится новой частью работы (`.scratch/<часть>-review-<N>/`: описание → спека → тикеты → ревью) или **отложить** — запись в `KNOWN_ISSUES.md`. Круги повторяются, пока ревью не найдёт ничего, что решено чинить.

В начале тикета — строка `Сложность:` (`простой`, `средний`, `сложный`; по ней владелец выбирает модель, `docs/sessions-models.md`) и строка `Статус:` с одним из значений: `открыт`, `ждёт проверки`, `принят`. Та же строка — в начале описания, спеки и ревью.

## Одна сессия — один шаг

Шаг сессии — одно описание, одна спека, набор тикетов одной спеки, один тикет или одно ревью. Сессия не начинает следующий шаг сама, даже если время есть.

**Начало сессии.** Прочитать `CLAUDE.md`, `PROJECT_CONTEXT.md` (строка «Следующий шаг»), `CONTEXT.md`, этот файл и файлы текущей части в `.scratch/`. Сессии с кодом (тикет, ревью) читают ещё `docs/coding-standards.md` и `docs/code-map.md`. `docs/history.md` — только когда нужны подробности прошлой работы. Владелец обычно пишет просто «дальше» — значит, делать то, что в «Следующем шаге».

**Конец сессии.**

1. Коммит и отправка в рабочую ветку сессии (`git push -u origin <ветка>`). Это разрешено без отдельного «ок»: в рабочей ветке изменения ждут проверки.
2. Для тикета — инструкция по проверке (ниже). Для описания, спеки, тикетов и ревью — что прочитать и какие решения нужны от владельца.
3. Кнопки — инструмент выбора варианта (`AskUserQuestion`) с вариантами «ОК» и «Есть замечания».
4. **«ОК»:** статус шага — `принят`; в `PROJECT_CONTEXT.md` — что сделано (одна-две строки; подробности — в `docs/history.md`, карта кода и тестов — в `docs/code-map.md` и `docs/tests-map.md`) и новая строка «Следующий шаг» (с моделью и effort для неё по `docs/sessions-models.md`); коммит, отправка в рабочую ветку, затем перенос в `master`. Перенос: если `master` не ушёл вперёд — `git push origin HEAD:master`; если ушёл — сначала слить `master` в рабочую ветку, прогнать тесты, отправить и только потом переносить. Историю `master` не переписывать.
5. **«Есть замечания»:** исправить, отправить в рабочую ветку, снова инструкция и кнопки.

## Инструкция по проверке тикета

Пишется по правилам `CLAUDE.md` («Как писать инструкции владельцу»), всегда в таком порядке (сессия на ПК делает шаги 1–3 сама, ниже «Сессия на ПК владельца»):

1. **Остановить** бота: `.\stop-bot.ps1` (бот работает только в одном экземпляре). Старый бот, запущенный не через Docker (из `.venv`), `.\start-bot.ps1` остановит сам.
2. **Обновить файлы на ПК** через GitHub Desktop: открыть репозиторий `Telegram-bot`, в «Current branch» выбрать рабочую ветку **этой** сессии (назвать её точно: у каждой облачной сессии своя ветка), нажать «Fetch origin», затем «Pull origin».
3. **Запустить** — `.\start-bot.ps1` (PowerShell, папка проекта; после обновления файлов сам пересобирает образ, первая сборка — несколько минут).
4. **Проверить** — что открыть в браузере (`http://localhost:8080`), что отправить в Telegram (точный текст), что должно появиться и что значит «не так».
5. Бот после проверки **остаётся работать** (это его обычное состояние); `.\stop-bot.ps1` — только если остановка нужна.

Бот работает в Docker (ADR 0006, 0007); команды — `.\start-bot.ps1`, `.\stop-bot.ps1`, `.\logs-bot.ps1`, раздел «Запуск» в `CLAUDE.md`.

## Где работает сессия

- **В облаке** (так было до 2026-10-30): сессия не может ничего запускать на ПК владельца. Она пишет код, гоняет тесты у себя и даёт инструкцию; обновляет файлы и запускает приложение владелец. Тесты в облаке (файла `.env` нет, нужны фиктивные значения):
  `TELEGRAM_BOT_TOKEN=123456:dummy-token-for-tests TMDB_API_KEY=dummy ALLOWED_TELEGRAM_USER_IDS=1 python -m pytest tests/ -q`
  Настоящего бота в облаке не запускать: нет токена, и он может работать только в одном экземпляре. Образ можно собирать и запускать для проверки Docker с фиктивным `.env` (без настоящего токена бот повторяет подключение, веб работает; `dockerd &`, папка `data` и `.env` после проверки удаляются). В облаке Docker Hub может отвечать 429 — образ `python:3.12-slim` берётся из `mirror.gcr.io/library/python:3.12-slim` (`docker tag` под обычным именем), а сборка идёт копией `Dockerfile` со строками про сертификат прокси (`COPY --from=ca …`, `ENV PIP_CERT=…`, `--build-context ca=/root/.ccr`): без них `pip` внутри сборки не доверяет прокси.
- **На ПК владельца** (так сейчас, с 2026-10-30: владелец работает в Claude Code на ПК): сессия сама обновляет файлы и запускает приложение; владельцу остаётся проверка в браузере и Telegram. Порядок ниже.

### Сессия на ПК владельца

- **Папка** — `E:\LocalAI\Bionic\Telegram-bot`: здесь `.env`, `data` (база, журнал, копии) и `.venv`. Сессия работает прямо в ней, без отдельной копии: бот в Docker собирается из этих файлов.
- **Начало сессии:** `git fetch origin`, затем `git checkout master` и `git pull --ff-only` (в облаке могли остаться шаги, перенесённые в `master`); затем своя рабочая ветка от `master` (`git checkout -b claude/<часть>-<шаг>`). Рабочая копия должна быть чистой (`git status`); если в ней чужие изменения — не трогать, спросить владельца.
- **Тесты** — `.venv\Scripts\python.exe -m pytest tests/ -q` (полный набор — около 3 минут, удобно в фоне). Фиктивные значения не нужны: настройки берутся из `.env` (значения из него не выводить). Три теста про запуск процессов под Windows (`test_app_main`, `test_docker_files`, `test_runtime` — по одному) падают и без изменений; новые падения — нет.
- **Запуск для проверки — делает сессия, не владелец:** после коммита `.\start-bot.ps1` (сам останавливает прежний контейнер и старого бота из `.venv`, пересобирает образ и ждёт итога «Готово»), затем `http://localhost:8080/health` и строки журнала (`docker compose logs --tail 50`) — нет ли красного текста. Бота вне Docker (`python -m app.main`) не запускать: бот работает только в одном экземпляре.
- **Инструкция владельцу** — только блок «как проверить» (браузер, Telegram: точный текст и что должно прийти) и итог запуска одной строкой; шаги «остановить», «обновить файлы через GitHub Desktop» и «запустить» сессия сделала сама. Команды `.\stop-bot.ps1` и `.\start-bot.ps1` даются, только если владельцу нужно сделать это самому.
- **Конец сессии** — как выше: коммит, `git push -u origin <ветка>`, кнопки. После «ОК» и переноса в `master` рабочая копия остаётся на ветке сессии (в ней то же, что в `master`); следующая сессия сама перейдёт на `master`.
- GitHub Desktop владельцу больше не нужен для обновления файлов; если он открыт, он просто показывает текущую ветку.
