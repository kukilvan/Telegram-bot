# 27: Переносы дат не теряются, сводка не попадает в тихие часы

**Сложность:** обычный

**What to build:** два редких случая, в которых владелец молча не получает событие.
1. Ключ дедупликации переноса даты содержит только новую дату. Перенос туда-обратно-туда (15 дек → 22 янв → 15 дек → 22 янв) — третье сообщение считается уже известным и не приходит. То же у переноса серии сериала и аниме.
2. Ядро позволяет сохранить час сводки внутри тихих часов (например, 22:00 при тихих часах 21:00–7:30). Тогда в рабочие дни бот молчит весь день, и события приходят только в выходной.

Разбор: `review-2-problems.md`, Н4 и Н5.

**Blocked by:** —

**Status:** done (ждёт проверки владельцем)

## Ключ переноса (`movie_events.py`, `series_events.py`, `pollers/movie.py`)

- Ключ переноса = прежний ключ + момент предыдущего взгляда (`observed_at` сохранённого снимка, `%Y%m%dT%H%M%S`): `movie:<id>:date_moved:<новая дата>:from:<момент>`, `<тип>:<id>:s<N>:e<M>:moved:<новый момент>:from:<момент>`.
- `movie_events.detect_events` получает момент предыдущего взгляда вместо одной даты `observed_on`. Дата по-прежнему нужна правилам «вышел в кино» / «цифровой релиз» — её берём из момента. `MoviePoller.apply` передаёт `stored.observed_at`.
- `series_events._season_events` уже получает `observed_at` — добавить его в ключ переноса.
- Старые ключи в базе не трогаются (миграции нет).
- Комментарий у ключа объясняет, зачем момент: повтор после сбоя сохранения имеет тот же момент, новый перенос — другой.

## Проверка правил доставки (`delivery.py`, `settings_store.py`)

- `DeliveryRules`: метод проверки целостности — час сводки не внутри тихих часов (`is_quiet` для часа сводки). Если тихих часов нет — проверять нечего. Ошибка — `ValueError` с понятным текстом: «час сводки 22:00 попадает в тихие часы 21:00–07:30».
- `set_delivery_rules`: собрать будущие правила целиком (сохранённые + переданные), проверить и только тогда сохранить. Чтение, проверка и запись — подряд под `write_lock` (после тикета 29 — в сессии записи), чтобы два одновременных изменения не обошли проверку. При ошибке в базе ничего не меняется.
- `release`: если шаги кончились, а момент всё ещё внутри молчания, — предупреждение в журнал (такие правила могли быть сохранены до этого тикета). Поведение в остальном прежнее.
- `spec.md`, раздел «Доставка»: одна строка о запрете.

## Критерии

- [ ] Фильм: 15 дек → 22 янв → 15 дек → 22 янв по трём опросам — три события «премьера перенесена» (тест на точке ядра с поддельными часами и источником).
- [ ] Фильм: перенос найден, сохранение состояния упало, следующий опрос находит тот же перенос — одно событие, не два (тест).
- [ ] Серия сериала и серия аниме: то же туда-обратно-туда — три события (тесты).
- [ ] Событий старого вида в базе нет повторов после обновления: перенос, найденный до тикета, не приходит второй раз (тест: событие со старым ключом в базе, опрос с теми же данными).
- [ ] `set_delivery_rules(summary_at="22:00")` при тихих часах 21:00–7:30 — `ValueError`, правила в базе прежние (тест).
- [ ] `set_delivery_rules(quiet_from="14:00", quiet_until="16:00")` при сводке 15:00 — `ValueError` (тест: проверяются правила целиком, а не только переданное).
- [ ] Без тихих часов (начало равно концу) любой час сводки разрешён (тест).
- [ ] Набор тестов зелёный.
