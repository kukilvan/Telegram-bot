Пишется по принятому описанию `description.md` (эта папка). Находки — `.scratch/web-1-docker-and-skeleton/review.md`, Н1–Н7. Термины — `CONTEXT.md`. Решения: ADR 0006 (Docker на ПК владельца), 0007 (бот, опрос и веб — один процесс). Поведение, которое здесь не названо, остаётся как в спеке части 5.1 (`.scratch/web-1-docker-and-skeleton/spec.md`). Стандарты кода — `docs/coding-standards.md`.

## 0. Итог в трёх строках

- Сбой при запуске: Docker по-прежнему повторяет запуск, но об одном и том же сбое владелец получает одно сообщение сразу и дальше не чаще раза в сутки; копия базы перед той же миграцией делается один раз (Н1).
- Токен бота неверного вида — та же ошибка связи с Telegram, что и чужой токен: веб и опрос работают, бот повторяет подключение (Н2); пауза повтора сбрасывается после старта приёма (KI-14).
- `.\start-bot.ps1` не пускает `.env` со знаком `$` (Н3), останавливает только старого бота этого проекта (Н4), показывает сборку по ходу (Н5) и в конце говорит, запустилось ли приложение (вопрос 2). Проверка здоровья идёт без прокси (Н6), в вебе один список открытых адресов и имена разделов из словаря (Н7).

### Где спека уточняет описание

Эти места решены здесь и стоят того, чтобы владелец их увидел:

1. **`$` в `.env` не поддерживается, а запрещается** (раздел 3). Режим «читать `.env` как есть» в `docker compose` есть (`format: raw`), но проверка в облаке показала, что он не годится: кавычки, пробелы по краям и комментарий в конце строки он оставляет в значении (`WEB_PASSWORD="abc"` станет паролем с кавычками), а тесты читают `.env` иначе; и главное — `docker compose` всё равно читает тот же `.env` для своих подстановок (`WEB_PORT`), поэтому предупреждения про `$` остаются, а `${` без `}` ломает даже `.\stop-bot.ps1`. Поэтому `.\start-bot.ps1` находит `$` в `.env` **и не запускает** приложение, называя номер строки и имя настройки. Не запускать честнее, чем запустить с испорченным паролем.
2. **«Тот же сбой»** — тот же тип ошибки, те же места в коде (без номеров строк) и тот же текст ошибки, в котором все числа заменены одним знаком (раздел 1.2). Так время, номера и адреса в памяти не делают сбой «новым», а опечатка в другой настройке — делает.
3. **Напоминание говорит, что оно напоминание**: «Бот не запускается с 27.10 14:05» и когда будет следующее (раздел 1.5).
4. **«База не менялась с копии» проверяется по содержимому**: копия перед той же миграцией не делается, если в папке копий уже есть копия перед той же ревизией и её содержимое совпадает с базой (раздел 1.7). Время изменения файла для этого ненадёжно (режим WAL).
5. **`.\start-bot.ps1` ещё и подсказывает про токен неверного вида**: веб в этом случае работает и контейнер здоров, поэтому скрипт пишет «Готово», но добавляет строку «бот не подключён к Telegram: токен бота неверного вида…» (раздел 4, шаг 8). Без неё новичок, скопировавший `.env.example`, видит «Готово», а бот молчит. Чужой или отозванный токен правильного вида скрипт не распознаёт — только журнал.
6. **Проверка здоровья Docker в первую минуту после старта идёт каждые 2 секунды** (`--start-interval`, раздел 4.2), чтобы `.\start-bot.ps1` говорил итог через несколько секунд, а не через 30.

## 1. Сбой при запуске (Н1)

### 1.1 Что такое сбой запуска

Сбой запуска — исключение, которое вылетело из `main()` в `app/main.py` до начала работы, и пустой `ALLOWED_TELEGRAM_USER_IDS` (раздел 1.6). Как сейчас: запись в журнал с трассировкой, отчёт владельцу в Telegram по простому HTTP (`send_startup_error_sync`), выход с кодом 1, Docker поднимает контейнер снова (`restart: unless-stopped`; паузы растут до 1 минуты). Новое — только решение, отправлять ли отчёт (разделы 1.2–1.4).

Смерть части во время работы (веб, бот, сторож; `Runtime.run` вернул 1) сбоем запуска не считается и, как сейчас, в Telegram не сообщается. Сбой старта контейнера (`app/container_start.py`, `PUID`) — тоже как сейчас: только журнал.

### 1.2 Отпечаток сбоя

Отпечаток — строка SHA-256 от трёх частей исключения, пойманного в `run()`:

1. **Тип:** модуль и имя класса (`zoneinfo._common.ZoneInfoNotFoundError`).
2. **Места:** для каждого кадра трассировки этого исключения — имя файла без папок и имя функции, по порядку. Номера строк не входят: обновление кода сдвигает строки, а сбой тот же.
3. **Текст:** `str(исключения)` после маскировки секретов (`mask_secrets`); каждое `0x` с шестнадцатеричными цифрами и каждая группа цифр заменяются на `#`; пробелы и переводы строк схлопываются в один пробел; берутся первые 300 знаков.

Цепочка причин (`__cause__`, `__context__`) не входит. В файл пишется только отпечаток — ни текста, ни трассировки (там могут быть значения из `.env`).

Примеры (обязательны в тестах): `ZoneInfoNotFoundError('No time zone found with key Europe/Moskva')` дважды — один отпечаток; то же с `Europe/Mosсow` — другой; `ValueError` с текстом, где меняются время `2026-10-27 14:05:31` и адрес `0x7f3a2c1b9e50`, — один отпечаток; одна и та же ошибка, брошенная с разных строк одной функции, — один; из разных функций — разные; `TimeoutError` и `ConnectionError` с одинаковым текстом — разные.

### 1.3 Запись о сбое

Файл `data/startup_failure.json` (папка `data` — та же, что у базы и `web_secret`): `fingerprint` — отпечаток, `first_seen` — когда этот сбой случился впервые, `reported_at` — когда о нём в последний раз ушёл отчёт или `null`. Время — UTC, ISO 8601.

- Файла нет, он не читается или испорчен — считается, что записи нет.
- Запись не удалось сохранить (нет прав на `data`, KI-4 на NAS) — предупреждение в журнал, отчёт всё равно уходит (лучше лишнее сообщение, чем молчание), запуск дальше идёт как обычно (код 1).
- **Удачный запуск удаляет запись:** когда `main()` дошёл до `Runtime.run` (настройки, база, ядро и веб-приложение собраны). Если запись была — строка в журнал «сбой запуска (с <first_seen>) больше не повторяется». Не удалилась — предупреждение, работа продолжается. Поэтому тот же сбой, случившийся снова через неделю, сообщается сразу.

### 1.4 Когда отчёт уходит

Отчёта нет, если некуда слать: настройки не прочитались или нет `owner_chat` (как сейчас); тогда запись не трогается.

| Запись | Что делаем |
|---|---|
| Нет, или отпечаток другой | **Новый сбой:** отчёт сразу; запись `first_seen` = сейчас, `reported_at` = сейчас, если отчёт ушёл (Telegram ответил 200), иначе `null` |
| Тот же отпечаток, `reported_at` = `null` (прошлый отчёт не ушёл) | Отчёт сразу (напоминание) |
| Тот же отпечаток, от `reported_at` прошло 24 часа и больше, или `reported_at` позже текущего времени (часы перевели назад) | Отчёт-напоминание; `reported_at` = сейчас, если ушёл |
| Тот же отпечаток, прошло меньше 24 часов | Отчёта нет; в журнал строка «отчёт о сбое запуска уже отправлен <reported_at>, следующее напоминание после <reported_at + 24 ч>» |

Тихие часы и рабочие дни на отчёт не влияют (настройки могут быть сломаны) — поэтому напоминание раз в сутки, а не чаще.

Для этого `send_startup_error_sync` (или её замена) сообщает, ушёл ли отчёт. Правило — в отдельном модуле без сети и без чтения настроек (предложение: `app/startup_report.py`): на вход отпечаток, запись, текущее время; на выход — слать ли и какой будет запись. Часы и путь к файлу передаются, чтобы тесты подставляли свои.

### 1.5 Текст отчёта

Заголовок и одна-две строки над трассировкой (трассировка — как сейчас: `<pre>`, конец трассировки, секреты скрыты, не длиннее лимита Telegram):

- новый сбой: «⚠️ **Бот не запустился.** Docker повторяет запуск каждую минуту. Об этом же сбое напомню через сутки, если он не пройдёт; о другом сбое — сразу.»
- напоминание: «⚠️ **Бот всё ещё не запускается** (с 27.10 14:05). Следующее напоминание — через сутки.»

Время `first_seen` — по часам контейнера (`TZ` выставляется из `BOT_TIMEZONE` при старте контейнера; пояс неизвестен — UTC), вид `ДД.ММ ЧЧ:ММ`. Отчёты об ошибках во время работы (`ErrorMiddleware`, «Bot Error») не меняются.

### 1.6 Пустой `ALLOWED_TELEGRAM_USER_IDS`

Становится обычным сбоем запуска: `main()` бросает исключение с текстом «ALLOWED_TELEGRAM_USER_IDS пуст: бот не запускается открытым для всех. Впишите в .env свой номер Telegram (узнать — @userinfobot)». Дальше — разделы 1.2–1.5: отчёт уходит, если задан `OWNER_CHAT_ID` числом (первого разрешённого пользователя нет); иначе только журнал (критическая запись, как сейчас).

### 1.7 Копия базы перед миграцией

`_backup_before_migration` в `app/tracker/db.py`, до копирования:

1. Ревизия базы не последняя (как сейчас) — ищет в папке `backups` копии с именем `tracker_db_<время>_before-<та же ревизия>.db` и берёт самую новую по времени в имени.
2. Такая есть и её содержимое совпадает с базой — новая копия **не делается**; строка в журнал «копия перед миграцией с <ревизия> уже есть: <файл>; база с тех пор не менялась». Миграция идёт дальше.
3. Иначе — копия, как сейчас.

**Совпадает** — одинаковый текстовый дамп SQLite (`sqlite3.Connection.iterdump()`: схема и все строки всех таблиц) базы и копии; сравнивать можно потоком или по хешу, целиком в память не читать. Копию не удалось открыть или прочитать — она не считается совпадающей (делается новая). Дамп нужен только когда копия с той же ревизией уже есть, то есть почти только при повторе после сбоя миграции; на базе в десятки мегабайт это секунды раз в минуту — допустимо.

Почему так: упавшая миграция откатывается целиком (она идёт в одной транзакции), база остаётся той же, и копия с прошлого раза годится. Если миграция успела что-то записать мимо транзакции или владелец подложил другую базу той же ревизии, содержимое отличается — и копия делается заново.

## 2. Токен неверного вида (Н2) и KI-14

### 2.1 Токен неверного вида

Неверный вид — то, на что aiogram отказывается создать бота (`TokenValidationError`): пусто, нет `:`, слева от `:` не число, справа пусто, есть пробел. Проверка — тем же `aiogram.utils.token.validate_token`, своих правил не пишем.

- В `main()`: токен неверного вида — **запуск продолжается** без объекта `Bot`. Одна запись в журнал при запуске (`error`): «токен бота неверного вида — проверьте TELEGRAM_BOT_TOKEN в .env». Значение токена не пишется (его скрывает и форматтер, но пустой токен скрывать нечем, а длинный текст из `.env.example` не секрет — всё равно не пишем).
- Часть «бот» (`TelegramPart`): `connect` бросает исключение с тем же текстом; `receive` и `stop` не вызываются без удачного `connect`; `close` ничего не делает. Runtime повторяет подключение по своим правилам (30 с, дальше вдвое, до 5 минут) — так в журнале раз в 5 минут та же понятная запись. Токен не перечитывается: исправленный `.env` подхватывается перезапуском (`.\start-bot.ps1`).
- Отправка событий (`TelegramSender`) без бота бросает исключение с тем же текстом; очередь доставки считает это неудачной отправкой, как при отсутствии связи: событие остаётся в очереди, попытка повторяется со следующим проходом (как сейчас для любой ошибки отправителя).
- Веб, опрос, копии базы работают; `/health` — `200` (ожидание повторного подключения — «бот работает», как в спеке 5.1); контейнер `healthy`.
- Отчёт о сбое запуска здесь не нужен (это не сбой запуска), да и слать его нечем.

Токен правильного вида, но чужой или отозванный, — как сейчас (`TelegramUnauthorizedError` из `connect`, повтор).

### 2.2 KI-14: когда пауза сбрасывается

Пауза повтора возвращается к 30 секундам **после старта приёма**, а не после `connect`. Старт приёма — событие `startup` диспетчера aiogram (`start_polling` вызывает его после своей подготовки, перед циклом получения сообщений). Часть «бот» сообщает о нём runtime; как — решает тикет (например, `receive(started)` с вызовом из обработчика `dispatcher.startup`). Runtime по-прежнему не знает об aiogram.

Итог для журнала: подключение удалось, а приём падает сразу — паузы растут 30 → 60 → … → 300 с; приём успел начаться и потом упал — следующая пауза 30 с. KI-14 → «Исправлено (тест: …)».

## 3. Знак `$` в `.env` (Н3)

**Что проверено** (облако, `docker compose` 5.6.1, 2026-10-27; тот же разбор у Docker Desktop):

| Строка `.env` | Обычный режим `env_file` | `format: raw` | python-dotenv (тесты, `.venv`) |
|---|---|---|---|
| `A=Qwe$rty12345` | `Qwe` | `Qwe$rty12345` | `Qwe$rty12345` |
| `B=pa$$word123` | `pa$word123` | `pa$$word123` | `pa$$word123` |
| `C="quoted value"` | `quoted value` | `"quoted value"` | `quoted value` |
| `E=abc # comment` | `abc` | `abc # comment` | `abc` |
| `F=  spaced  ` | `spaced` | `  spaced  ` | `spaced` |
| `G=abc${def` | весь `docker compose` падает: «Invalid template» | то же | `abc${def` |

В обоих режимах `docker compose` отдельно читает `.env` для подстановки `${WEB_PORT}` в `docker-compose.yml` — отсюда предупреждения «The "rty12345" variable is not set» и падение на `${`. `format: raw` от этого не спасает и ломает кавычки и комментарии, поэтому не берётся. `docker-compose.yml` не меняется.

**Решение:**

- `.\start-bot.ps1` до запуска Docker ищет `$` в строках `.env`, кроме пустых и комментариев (первый непробельный знак — `#`). Нашёл — для каждой такой строки: «В файле .env в строке <номер> (<имя настройки>) есть знак $ — Docker его портит, и значение (например, пароль) перестанет подходить.», затем «Уберите знак $ из значения (для WEB_PASSWORD — придумайте пароль без него) и запустите скрипт снова.» и выход 1. Значение строки на экран **не выводится** (там может быть секрет), только номер и имя слева от `=`.
- `.env.example`: в первом абзаце строка «Не используйте в значениях знак $: Docker его портит, и .\start-bot.ps1 не запустит бота, пока он есть.»; у `WEB_PASSWORD` — «без знака $».
- Если когда-нибудь понадобится `$`, решение пересматривается (например, `.env` читается самим приложением, а `docker compose` получает отдельный файл для подстановок) — это не этот круг.

## 4. `.\start-bot.ps1` (Н4, Н5, вопрос 2)

### 4.1 Шаги скрипта

Шаги 1–3 — как сейчас (Docker установлен, Docker Desktop запущен, `.env` есть). Дальше:

4. **`$` в `.env`** — раздел 3.
5. **Старый бот из `.venv` (Н4).** Останавливаются только процессы `python.exe`, в командной строке которых модуль запускается целой командой: `-m app.bot.main` или `-m app.main`, перед `-m` — пробел или начало строки, после имени модуля — пробел, кавычка или конец строки (регулярное выражение вида `(^|\s)-m\s+app\.(bot\.)?main(\s|"|$)`). `uvicorn app.main:app`, `-m app.mainframe`, `-m myapp.main` не останавливаются. Были такие — «Остановлен старый бот, запущенный не через Docker» (как сейчас).
6. **Сборка и запуск (Н5):** `docker compose up -d --build`; каждая строка вывода (и обычного, и ошибок) появляется в окне сразу, как её напечатал Docker, и одновременно запоминается для подсказки про порт. Красных «NativeCommandError» от PowerShell быть не должно: строки ошибок Docker печатаются как обычный текст. Не получилось — как сейчас: «Не удалось запустить, ошибка выше», подсказка про `WEB_PORT=8081` при «port is already allocated» или «bind», выход 1.
7. **Ожидание итога (вопрос 2).** «Жду запуска приложения (до 90 секунд)…», затем раз в 2 секунды состояние контейнера сервиса `tracker` (`docker compose ps -q tracker`, `docker inspect`: статус, здоровье, число перезапусков). Число перезапусков запоминается сразу после шага 6.
   - здоровье `healthy` — шаг 8;
   - статус `restarting`, `exited` или `dead`, число перезапусков выросло, или здоровье `unhealthy` — «Запуск не удался. Последние строки журнала:», последние 30 строк журнала контейнера (`docker compose logs --no-color --tail 30 tracker`), затем «Полный журнал: .\logs-bot.ps1. Docker будет пробовать запустить снова каждую минуту; остановить — .\stop-bot.ps1. Исправьте причину и запустите этот скрипт снова.» и выход 1;
   - 90 секунд прошли, здоровье всё ещё `starting` — «Приложение запускается дольше обычного. Через минуту откройте http://localhost:<порт>/health или посмотрите журнал: .\logs-bot.ps1» и выход 0 (медленный старт — не сбой).
8. **Готово.** «Готово. Бот работает в Docker. Приложение: http://localhost:<порт>» (порт — как сейчас). Если в журнале контейнера с его последнего старта есть запись «токен бота неверного вида» (раздел 2.1) — следом «Внимание: бот не подключён к Telegram — токен бота неверного вида. Проверьте TELEGRAM_BOT_TOKEN в .env и запустите скрипт снова. Веб работает.» Выход 0.

Если контейнер не пересоздавался (ничего не менялось) и уже был здоров, шаг 7 сразу видит `healthy`.

Файл по-прежнему UTF-8 с BOM, `Set-Location $PSScriptRoot` в начале. `stop-bot.ps1` и `logs-bot.ps1` не меняются.

### 4.2 `Dockerfile`

`HEALTHCHECK --interval=30s --timeout=10s --start-period=60s --start-interval=2s --retries=3 CMD ["python", "-m", "app.healthcheck"]`: в первые 60 секунд проверка идёт каждые 2 секунды, и контейнер становится `healthy` через несколько секунд после того, как веб начал слушать. `--start-interval` есть в Docker Engine с версии 25 (у владельца 29.x). Тикет проверяет в облаке, что образ собирается и контейнер становится `healthy` за ≤ 15 секунд.

## 8. Тесты и проверка

Все тесты без сети, как остальные; идут и на Windows (`tests` запускаются владельцем через `.venv`). Сейчас тестов 1141, после круга — все проходят, `pyflakes app tests` чистый.

**Сбой запуска (`app/startup_report.py` или как назовёт тикет; часы и файл подставные):**
- отпечаток: все примеры раздела 1.2; в отпечатке нет текста (в файле записи нет слов из ошибки и значения токена);
- таблица 1.4 построчно: нет записи → отчёт; тот же сбой через 1 минуту, 23 ч 59 мин → нет; через 24 ч → напоминание; другой сбой через минуту → отчёт; `reported_at` = `null` → отчёт; `reported_at` в будущем → отчёт; отчёт не ушёл → `reported_at` остаётся `null`;
- испорченный файл записи → как без записи; файл не пишется (подставная запись бросает `OSError`) → отчёт уходит, исключение не вылетает;

- текст: новый сбой и напоминание (раздел 1.5), время `first_seen` в виде `ДД.ММ ЧЧ:ММ`.

**Копия перед миграцией (`app/tracker/db.py`, временная папка, настоящие файлы SQLite):**
- база старой ревизии, миграция падает (подставная) дважды → одна копия `before-<ревизия>`;

## 9. Крайние случаи

| Случай | Что происходит |
|---|---|
| Сбой запуска сам прошёл через 5 минут (папка `data` на NAS подключилась позже) | Одно сообщение «Бот не запустился», дальше бот работает, запись удалена |
| Сбой → исправили → через неделю тот же | Сообщение сразу (запись удалена удачным запуском) |
| Сбой A, потом B, потом снова A в те же сутки | Три сообщения: каждый — новый сбой для записи, помнящей только последний |
| Текст ошибки меняется не только числами (случайное имя файла) | Каждый повтор — новый сбой, сообщение раз в минуту. Не встречали; → `KNOWN_ISSUES.md` |
| Нет прав на `data` — запись не сохраняется | Сообщение при каждом повторе (раз в минуту) плюс предупреждение в журнале. Обычно в этом случае не открывается и база, и сбой тот же → `KNOWN_ISSUES.md` |
| ПК был выключен двое суток во время сбоя | После включения — напоминание сразу (прошло больше суток) |
| Нет интернета при сбое запуска | Отчёт не ушёл (`reported_at` = `null`), при следующем повторе пробует снова |
| Сломанная миграция, база 50 МБ | Одна копия; дважды в минуту дамп базы и копии для сравнения — секунды |
| Токен неверного вида и события в очереди | Ждут в очереди; после исправления `.env` и `.\start-bot.ps1` приходят (как после отсутствия связи) |
| Токен правильного вида, но чужой | Как сейчас: повтор подключения, журнал; `.\start-bot.ps1` пишет «Готово» без подсказки |
| `$` в комментарии в конце строки (`WEB_PORT=8080 # $`) | Скрипт тоже не пускает — лишняя строгость, безвредна |
| Другой проект на ПК запущен ровно как `python -m app.main` | `.\start-bot.ps1` остановит и его (имя модуля то же). Редко → `KNOWN_ISSUES.md` |
| Первая сборка 5 минут | Ожидание итога начинается после сборки: 90 секунд хватает с запасом |
| Docker Desktop старее 25 | Сборка падает на `--start-interval` с ошибкой Docker. У владельца 29.x; для шаблона (кусок 8) — требование версии в README |

**В `KNOWN_ISSUES.md`** записываются тикетом, который вводит поведение (номера — следующие по порядку, KI-16 и дальше): сбой с меняющимся текстом; запись о сбое не сохраняется; остановка чужого `python -m app.main`. KI-14 → «Исправлено (тест: …)».

## 10. Что не входит

Как в описании: Н8–Н14 (кроме KI-14), показ в вебе, что бот не подключён к Telegram (вернуться в части 5.4), замечания «оставить как есть», другие правила перезапуска Docker.
