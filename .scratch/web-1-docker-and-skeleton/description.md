# Кусок 5, часть 1: бот в Docker и каркас веб-приложения

Статус: ждёт проверки

Термины — из `CONTEXT.md`. Решения, на которые опирается часть: ADR 0002 (веб — главный интерфейс), 0004 (FastAPI + HTMX), 0005 (SQLite в режиме WAL), 0006 (Docker на ПК владельца, проверка по `localhost`). Известные проблемы, которые здесь чинятся: KI-3 и KI-4 (`KNOWN_ISSUES.md`).

## Зачем

Сейчас бот запускается из окна PowerShell (`.\start-bot.ps1`): закрыл окно — бот остановился, перезагрузил ПК — надо запускать заново. Веб-приложения нет совсем.

По ADR 0006 всё будет работать в Docker на ПК владельца, и с этой части каждое следующее изменение проверяется уже в Docker. Поэтому первая часть куска 5 закладывает основу, на которой строятся все экраны: бот и веб-приложение собраны в один Docker-образ, работают с одной базой, сами поднимаются после перезагрузки ПК, а в браузере открывается пустой, но настоящий каркас приложения со входом по паролю.

## Что увидит владелец после этой части

1. **Бот запускается одной командой через Docker**, а не из окна PowerShell. Окно можно закрыть — бот продолжает работать. После перезагрузки ПК бот поднимается сам, как только запустится Docker Desktop (если в Docker Desktop включён автозапуск при входе в Windows), и догоняет пропущенное.
2. **В Telegram всё как раньше:** те же кнопки «➕ Добавить», «📚 Мои тайтлы», «Сводка сейчас», «Тестовое событие», тот же список. База не теряется: Docker берёт тот же файл `data/tracker.db`, что и сейчас.
3. **В браузере на том же ПК** по адресу `http://localhost:8080` открывается страница входа. После ввода пароля — каркас приложения: меню с разделами «Лента», «Список», «Архив», «Поиск», «Настройки» (пока заглушки «скоро будет») и строка с живыми данными из базы, например «В списке 12 тайтлов · последняя проверка источников в 14:05». По этой строке видно, что веб и бот работают с одной базой.
4. **Неверный пароль** — страница входа с сообщением; после нескольких неверных попыток подряд вход на время блокируется.
5. **Docker Desktop показывает контейнер как «healthy» (здоров)**, а не «unhealthy», как было бы со старой проверкой (KI-3). Если бот или веб перестали отвечать — пометка меняется, и Docker перезапускает контейнер.
6. **Журнал и копии базы** лежат в папке проекта на ПК, как и раньше, и не пропадают при пересборке контейнера. Журнал можно смотреть и в Docker Desktop (вкладка «Logs»), и командой.
7. **Простые команды для владельца:** запустить (с пересборкой после обновления файлов), остановить, посмотреть журнал. Старый способ запуска через `.venv` для бота больше не используется (тесты по-прежнему идут через `.venv`), а `.\start-bot.ps1` перестаёт запускать второй экземпляр бота — бот может работать только в одном экземпляре.

## Что входит

- **Один Docker-образ и один `docker compose`** для бота и веб-приложения.
- **Бот, опрос источников, доставка, копии базы и веб — в одном процессе.** Почему так (а не два контейнера) — вопрос 1 ниже.
- **Каркас веб-приложения на FastAPI + HTMX** (ADR 0004): общий шаблон страницы с меню, заглушки разделов, одна строка живых данных через фасад ядра `Tracker`. Библиотека HTMX лежит в проекте, а не грузится из интернета, — приложение должно открываться и без внешних сайтов.
- **Вход по одному паролю:** пароль задаётся в `.env`, в браузере сохраняется сессия (повторно пароль не спрашивается, пока не истечёт), блокировка после нескольких неверных попыток подряд. Все страницы, кроме входа и проверки здоровья, закрыты паролем.
- **Веб открыт только для самого ПК:** порт публикуется на `127.0.0.1`, с телефона или другого компьютера в домашней сети страница не откроется. Доступ снаружи — кусок 7 (ADR 0006).
- **Исправление KI-3:** проверка здоровья через собственную страницу приложения (отвечает, только если работают и веб, и фоновые задачи бота), без программы `pgrep`, которой нет в образе.
- **Исправление KI-4:** процесс в контейнере работает не от `root` и всё равно может писать в подключённые папки на Linux (NAS): права на папки выставляются при старте контейнера, номер пользователя можно задать в `.env` (так принято на NAS).
- **Переписать раздел «Запуск» в `CLAUDE.md`**, раздел 4 `PROJECT_CONTEXT.md` и инструкцию проверки в `docs/agents/workflow.md` под Docker; новые переменные `.env` — в таблицу раздела 10 `PROJECT_CONTEXT.md`.
- Тесты: каркас веба (вход, блокировка, закрытые страницы, страница здоровья) — без сети, как остальные. Сборка образа и права на папки проверяются запуском Docker (в облачной сессии — если там удастся запустить Docker; на ПК владельца — по инструкции).

## Что не входит

- Сами экраны: Лента, Список, карточка, Архив, Поиск, оценки, Настройки — следующие части (ниже).
- Временные кнопки бота «➕ Добавить», «📚 Мои тайтлы», «Карточка» остаются — см. вопрос 4.
- Кнопка «Открыть приложение» в боте, кнопка «Открыть» под событиями и вход из Telegram без пароля: Telegram открывает мини-приложение только по адресу `https://`, а у нас пока `http://localhost`. Это кусок 7 (доступ вне дома).
- Установка на телефон (PWA) — по той же причине проверяется в куске 7; манифест можно добавить раньше (часть 4).
- Выгрузка в JSON/CSV, облачные копии, NAS, Tailscale или Cloudflare Tunnel — кусок 7.
- Игры — кусок 6.

## Решения, которые нужны от владельца

1. **Один процесс или два контейнера.** Рекомендую **один процесс в одном контейнере**: бот, опрос и веб работают вместе. Тогда у ядра одна копия, миграции базы и копии делаются в одном месте, кнопка в вебе может сразу что-то отправить в Telegram, а правило «только один экземпляр бота» соблюдается само. Минус: если упадёт веб, перезапустится и бот (Docker делает это сам за секунды). Два контейнера (бот отдельно, веб отдельно) надёжнее разделены, но им нужно договариваться, кто мигрирует базу и кто шлёт в Telegram, — для одного владельца это лишняя сложность.
2. **Вход по паролю — в этой части или позже.** Рекомендую **в этой**: пока веб открыт только для самого ПК, пароль почти не нужен, но каждая следующая страница строится уже за входом, и потом не придётся переделывать. Пароль — строка в `.env` (как токен бота).
3. **Адрес `http://localhost:8080`.** Порт 8080 можно поменять в `.env`, если он уже занят другой программой на ПК. Нужен другой — напишите.
4. **Когда убирать временные кнопки бота «Добавить» и «Мои тайтлы».** По спеке они уходят в куске 5, когда их заменит веб. Но веб до куска 7 открывается только на ПК, а с телефона — нет. Рекомендую **оставить кнопки до куска 7** (когда веб откроется с телефона) и убрать их там. Если вы и так не пользуетесь ботом до живой проверки (кусок 9), их можно убрать в конце куска 5 — скажите.

## Как поделить кусок 5 (предложение)

Каждая часть проходит полный путь (описание → спека → тикеты → тикеты по одному → ревью), поэтому части крупные: так меньше служебных сессий.

| Часть | Что входит | Чем полезна сама по себе |
|---|---|---|
| **5.1** (эта) | Docker для бота и веба, KI-3, KI-4, каркас FastAPI + HTMX, вход по паролю | Бот живёт в Docker и сам поднимается; в браузере открывается приложение |
| **5.2** | Поиск с подсказками и добавление; Список с фильтрами по типу и статусу; карточка тайтла: сезоны и отметки, смена статуса, «Посмотрел», «Следить», удаление | Всё, что сейчас делают кнопки бота, можно делать в браузере |
| **5.3** | Лента (что выходит и что вышло, по датам), Архив с поиском и сортировкой, оценки (новая таблица в базе) | Главный экран и то, чего в боте не было: архив и оценки |
| **5.4** | Настройки (часовой пояс, рабочие дни, час сводки, тихие часы, порог частей сезона), PWA-манифест и значок, по решению 4 — уборка временных кнопок бота | Правила доставки меняются без правки базы; приложение готово к установке на телефон |

**Оценка.** Строка дорожной карты «3–4 сессии» для куска 5 написана до порядка «одна сессия — один шаг». По новому порядку на часть уходит 4 служебные сессии (описание, спека, нарезка, ревью) плюс по сессии на тикет (в части 3–6 тикетов) и, возможно, круг исправлений после ревью. Получается **около 30 сессий на кусок 5** (±30 %), из них примерно половина — простые тикеты для Sonnet. При «ОК» поправлю строку куска 5 в дорожной карте.

## Что может пойти не так (решается в спеке)

- **Бот и веб в одном цикле событий.** aiogram и веб-сервер оба хотят ловить сигнал остановки; нужно, чтобы `docker compose down` останавливал всё чисто, не обрывая запись в базу.
- **Окончания строк в Windows.** GitHub Desktop может переписать окончания строк в файлах на «виндовые», и скрипт запуска внутри контейнера (Linux) тогда не запустится. Нужен `.gitattributes` или запуск без shell-скрипта.
- **Два экземпляра бота.** Если запустить и Docker, и старый `.\start-bot.ps1`, Telegram отвечает ошибкой конфликта. Инструкция начинается с остановки старого бота, а сам скрипт больше не запускает бота из `.venv`.
- **Время в журнале.** В контейнере часы по UTC; журнал должен писать время владельца (`BOT_TIMEZONE`), иначе записи будут «на 3 часа раньше».
- **Права на папки (KI-4) на Windows не видны** — там Docker Desktop права не проверяет. Проверить по-настоящему можно только на Linux: в облачной сессии, если там запустится Docker, иначе — при переезде на NAS (тогда KI-4 остаётся с пометкой «исправлено, не проверено на NAS»).
