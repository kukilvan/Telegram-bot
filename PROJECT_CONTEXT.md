## 1. Цель

Личный трекер релизов фильмов, сериалов, аниме и игр для одного владельца. Бот сообщает о важных событиях (объявлена дата, вышла серия, игра вышла на моей платформе, скидка), хранит прогресс и оценки владельца. Основной интерфейс будущего продукта — веб-приложение (ADR 0002), Telegram-бот остаётся каналом доставки. Позже код выкладывается на GitHub как шаблон «сделай себе такого же» (новый репозиторий с чистой историей).

Что решено убрать (убрано в тикете 12; подробности в обсуждении перед ADR): заметки и теги, команды `/add`, `/remove`, `/watchlist`, `/note`, `/notes`, `/events`, `/search`, `/searchgame`, inline-поиск, подтверждение «уже вышел, добавлять?», события «Русская озвучка» и «KinoPub», источник RAWG и неофициальный запрос PSN, все хардкоды под владельца.

Раз в неделю архивный фильм проверяется по коллекции TMDb; новая часть коллекции, вышедшая позже фильма (или без даты), приходит событием «Анонсировано продолжение: …» с кнопкой «👀 Следить» — продолжение добавляется со статусом «Хочу» только по нажатию. Продолжения, которые уже были в коллекции в момент «Посмотрел», новостью не считаются. Событие есть в «Тестовом событии». Ждёт проверки владельцем.
- Тикет 05 (`release-tracker-v2`): «➕ Добавить» умеет сериалы (TMDb). Тайтл хранит сезоны с номером ≥ 1 (сезон 0 не считается) и их серии с датами. Карточка показывает текущий или последний вышедший сезон («Сезон 2: вышло 5 из 8, следующая — пн, 12 окт», неизвестное число серий — «из ?»), анонс — отдельной строкой («Сезон 4 анонсирован, премьера 8 июля 2027»). После добавления бот спрашивает, какие сезоны уже просмотрены (кнопки-переключатели), то же открывает кнопка «📺 Просмотренные сезоны» в карточке. Статус сам не меняется (тикет 08); опрос и события сериалов — тикет 06. Ждёт проверки владельцем.
- Тикет 06 (`release-tracker-v2`): ядро само опрашивает сериалы и присылает шесть событий: объявлена дата сезона, сезон начался, вышла серия N (с датой следующей), сезон закончился, дата серии сдвинулась («пн, 26 окт → пн, 2 ноя»), сериал закрыт или отменён (по статусу TMDb «Ended» / «Canceled»). Первая серия сезона приходит как «начался сезон», последняя как «сезон закончился» — отдельного сообщения «вышла серия» про них нет. Серия считается вышедшей с 00:00 UTC её дня (TMDb не даёт часа). Интервал проверки: серия через ≤2 дня — 1 ч, ≤14 дней — 6 ч, дальше или без даты — 24 ч, сериал закрыт и ничего не ждём — 7 дней. Все типы есть в «Тестовом событии». Ждёт проверки владельцем.
- Тикет 07 (`release-tracker-v2`): сезон, который выходит порциями, делится на части. Разрыв больше порога (по умолчанию 6 недель, настройка `part_gap_weeks` в таблице `settings`; ровно на пороге — ещё не разрыв) между соседними сериями одного сезона начинает новую часть. Части считаются из дат серий и нигде не хранятся, поэтому смена порога ничего не присылает. Карточка: «Сезон 3, часть 1: вышло 8 из 8; часть 2 — с 27 марта»; без разрыва текст прежний и частей не упоминает. Три новых события: объявлена дата части («часть 2 сезона 3», только если сезон уже идёт), началась часть, закончилась часть (с датой следующей части; если даты части 2 появились уже после выхода всей части 1, конец части 1 приходит одним сообщением вместо «объявлена дата»). Ключ дедупликации разделённого сезона содержит часть (`s3:p1:ended`), у сезона без разрыва ключи прежние. Три образца в «Тестовом событии». Владелец пока меняет порог только через ядро (`set_part_gap_weeks`), экран настроек — в веб-приложении (кусок 5). Ждёт проверки владельцем.
- Тикет 08 (`release-tracker-v2`): сериал сам меняет статус по отметкам сезонов и по статусу источника. Сезон «вышел» — если в нём есть вышедшая серия; сериал без вышедших сезонов статус не меняет. Закрыт = источник говорит «Ended» / «Canceled». Правило (с тикетом 18):

  | Закрыт? | Отмечено из вышедшего | Статус | Слежение |
  |---|---|---|---|
  | нет | всё | Жду | да |
  | нет | часть | В процессе | да |
  | нет | ничего | Хочу | да |
  | да | всё | Просмотрено (архив) | нет |
  | да | часть | Досмотреть | нет |
  | да | ничего | Хочу | да (раз в неделю, чтобы не пропустить возвращение) |

  Пересчёт идёт при отметке сезона, при добавлении и после каждого опроса; не опрашиваются тайтлы с выключенным слежением. Правило общее для сериалов и аниме (признак «сезонный» в таблице `kinds.py`); у аниме «закрыт» не определяется, работают строки «нет». Статус «Бросил» вручную пока не ставится. Ждёт проверки владельцем.
- Тикет 18 (`release-tracker-v2`, правка тикета 08 по ревью): новый статус «В процессе» (`in_progress`) для идущего сериала или аниме, у которого отмечена часть вышедших сезонов; раньше такой тайтл получал «Хочу», хотя по словарю «Хочу» — «не начал». «Жду», у которого вышел новый сезон, теперь становится «В процессе». Статус опрашивается (`POLLED_STATUSES`), пересчитывается автоматически (`AUTOMATIC_STATUSES`), в карточке подписан «В процессе». Миграции нет: пересчёт при ближайшем опросе или отметке сезона. Ждёт проверки владельцем.
- Тикет 09 (`release-tracker-v2`): «➕ Добавить» умеет аниме (Shikimori). Тайтл — франшиза целиком: цепочка строится от выбранной записи по связям `prequel` и `sequel` (других связей — побочные истории, спин-оффы, кроссоверы — не трогаем). Сезоны — записи tv и ONA (короче 10 минут не считаются: это мини-ролики); запись с «Part N», «Cour N», «N-й Cour» при N ≥ 2 в оригинальном названии (русское не читается) присоединяется к предыдущему сезону как часть; фильмы цепочки — отдельная строка «Фильмы франшизы: …» в карточке (если больше 5 — последние пять); OVA, спешлы, рекапы, PV пропускаются. Проверено на четырёх франшизах аудита: One Piece — 1 сезон; JJK — 4 сезона и фильм 0; Монолог фармацевта — 3 сезона, у третьего 2 части; Созданный в Бездне — 2 сезона и 5 фильмов. У каждой части (таблица `season_parts`) и каждого фильма (`franchise_movies`) свои Shikimori-, MAL- и AniList-id, повтор одного id в тайтле запрещён базой; если AniList держит две записи Shikimori как одну, id достаётся первой. Id AniList берутся одним запросом по MAL-id; сбой AniList не мешает добавлению (id остаются пустыми до опроса аниме, тикет 10, как и признак «фильм вышел» у фильмов франшизы). Кнопка «Добавить» → «Аниме» → название → одна подсказка на франшизу; после добавления бот спрашивает просмотренные сезоны (части сезона отмечаются вместе с сезоном). Любая запись франшизы открывает один и тот же тайтл. Опрос и события аниме — тикет 10; «закрыт» у аниме не определяется, поэтому автостатус даёт только «Хочу», «В процессе» и «Жду». Ждёт проверки владельцем.
- Тикет 10 (`release-tracker-v2`): ядро само опрашивает аниме и присылает те же события, что по сериалам (объявлена дата сезона или части, началась и закончилась часть или сезон, вышла серия N с датой следующей, дата серии сдвинулась; «закрыт» у аниме не определяется), плюс два новых: «анонсирован фильм франшизы» и «вышел фильм франшизы». Сообщения с иконкой 🎌, названием «Русское (Original)» и временем серии в часовом поясе владельца (`BOT_TIMEZONE`) с русским днём недели: «следующая: пт, 6 ноя в 16:00»; карточка аниме показывает время так же. Номер в сообщении — номер **вышедшей** серии. Состав серий собирается из двух источников: Shikimori говорит, какие сезоны и части есть и как далеко они ушли, AniList даёт точное расписание каждой ещё не законченной части (один запрос по id частей тайтла): вышло на одну серию меньше номера ближайшей, плюс её момент. Сбой AniList, пустой ответ или «дыра» в ответе ничего не затирают: даты остаются прежними, Shikimori добавляет только то, чего ещё не было. Часть, о которой AniList ничего не знает (или говорит «ничего не вышло, даты нет»), идёт по Shikimori, поэтому смена текущей части или сезона не теряется. Серия, которой не было в сохранённом, получает момент проверки, на которой её нашли, — так не теряется первая серия нового сезона; при добавлении тайтла всё вышедшее — история. Дата уже вышедшей серии остаётся такой, какой записана впервые. Опрос заполняет пустые AniList-id частей и фильмов. Интервал проверки как у сериалов (≤2 дня — 1 ч, ≤14 дней — 6 ч, дальше — 24 ч). Статусы тикета 08 работают как раньше. Фильмы франшизы берутся из Shikimori (`anons` — анонсирован); фильм, который появился в цепочке уже вышедшим с датой не позже прошлой проверки, новостью не считается. Ключ переноса даты серии содержит новую дату и, если известен час, минуту (второй перенос в тот же день — новое событие); замена даты без часа точным моментом того же дня переносом не считается; расписание AniList с номерами больше числа серий части (сквозная нумерация) не используется. Одиннадцать образцов в «Тестовом событии». Новая зависимость `tzdata` (часовые пояса на Windows). Ждёт проверки владельцем.
- Тикет 11 (`release-tracker-v2`): доставка подчиняется правилам владельца (часовой пояс — `BOT_TIMEZONE`, рабочие дни, час сводки и тихие часы — в таблице `settings`; по умолчанию вс–чт, 15:00, 21:00–7:30). Событие судится по моменту, когда оно попало в очередь: в тихие часы ждёт их конца; в рабочий день до 15:00 ждёт 15:00; иначе уходит сразу отдельным сообщением. Всё, что ждало, уходит **одним** сообщением «📋 Сводка · вс, 1 ноя»: в нерабочий день — в 7:30, в рабочий — в 15:00 (ночные события входят в эту сводку). Событие, которое появилось ровно в 15:00 или 7:30 нерабочего дня, уходит сразу, не сводкой. В тихие часы и в рабочее утро не уходит ничего, в том числе повтор после сбоя. Пустая сводка не отправляется; длинная режется на несколько сообщений (до 3500 знаков). В сводке каждое событие — одна строка (строки сообщения через « · »), кнопки событий («Посмотрел», «Следить», «Карточка») сохраняются с названием тайтла (не больше 10, но все «Следить» показываются всегда — других путей к ним нет; порядок: «Следить», «Посмотрел», «Карточка»; у каждой части разрезанной сводки свои кнопки). Событие, которое должно было уйти сразу, но не ушло из-за сбоя отправки и пережило тихие часы или рабочее утро, входит в сводку (7:30 или 15:00), а не приходит отдельно; повтор после сбоя в том же открытом окне (пятница 12:00 → 12:05) по-прежнему уходит отдельным сообщением (`DeliveryRules.next_silence` — ближайшее начало молчания: тихие часы или полночь рабочего дня; событие идёт в сводку, если оно ждало по правилам или это начало наступило не позже текущего момента). Серии одного сезона (части — отдельно) одного тайтла в сводке сворачиваются: «вышли серии 5–6», «3, 5–6, 9»; в немедленных сообщениях серии по-прежнему приходят каждая отдельно. «📋 Сводка сейчас» (кнопка и `/summary`) отправляет всё накопленное одним сообщением в любой час и помечает доставленным; пусто — бот отвечает, что присылать нечего. «Тестовое событие» из меню по-прежнему уходит сразу в обход правил; последний пункт его списка «🕒 Проверить правила доставки» (тикет 20; сначала была отдельная кнопка «Окна доставки») подставляет момент недели (вс 10:00, вс 16:00, пт 12:00, сб 10:00, чт 22:00, сб 22:00, пт 7:29, пт 7:30): отправляется образец «Сериал: две серии подряд» как будто в этот момент, затем разыгрывается момент выпуска и приходит сводка, бот пишет, что было бы. Настоящая очередь при этом не трогается. Настройки меняются пока только через ядро (`set_delivery_rules`), экран — в веб-приложении (кусок 5); часовой пояс из настроек перекрывает `BOT_TIMEZONE` и для часов серий аниме. Ждёт проверки владельцем.

В меню — «➕ Добавить» и «📚 Мои тайтлы» (временные, до веб-приложения), «📋 Сводка сейчас», «🧪 Тестовое событие» (проверочная; в тикете 20 в её список перенесена проверка правил доставки); `/start` показывает меню. ## 4. Как запускать и проверять

Запуск (PowerShell, Windows). Бот может работать только в одном экземпляре.

Остановить все экземпляры:
```powershell
Get-CimInstance Win32_Process -Filter "Name='python.exe'" | Where-Object { $_.CommandLine -like '*app.bot.main*' } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```
Запустить бота:
```powershell
cd E:\LocalAI\Bionic\Telegram-bot
.\start-bot.ps1
```
(скрипт сам переходит в свою папку, поэтому работает и из другой, например `C:\` с полным путём к нему; запускает `.venv\Scripts\python.exe -m app.bot.main` без `Activate.ps1`; если `.venv` нет, пишет по-русски, как его создать, и выходит; окно закрывать нельзя, остановка — `Ctrl+C`). Другого способа запуска нет: скрытый `launch_bot.py` удалён.

Тесты:
```powershell
.venv\Scripts\python.exe -m pytest tests/ -v
```
База трекера мигрируется сама при старте бота; вручную: `alembic -c alembic_tracker.ini upgrade head`. Docker: `docker build -t telegram-bot .` и `docker run --env-file .env -v ${PWD}/data:/app/data telegram-bot` (образ собирался и запускался; каталог `/app/data` хранит базу).

**Проверка после изменений:** остановить бота, запустить, 10–15 секунд смотреть консоль (красного текста быть не должно, через минуту появляется строка `poll scan done: … failed, …`), затем владелец отправляет сообщения, относящиеся к изменённому (инструкции — в `CLAUDE.md`, раздел «Как писать инструкции владельцу»). Сессия считается успешной, если в консоли нет ошибок и в Telegram не пришло сообщение об ошибке.

Логи: `app/logs/bot.log` (ротация 10 МБ × 5). Резервные копии базы трекера: `app/utils/backup.py` (при запуске и раз в час, если последней копии больше суток; перед миграцией; ротация 14 + 12; в `data/backups/`). Старая база и её копии — `data/archive/`.

## 5. Архитектура и карта кода

```text
Telegram (aiogram 3.x) → app/bot (тонкие обработчики) → app/tracker (ядро: события, доставка) → источники → app/providers → внешние API
База: SQLite в режиме WAL (SQLAlchemy 2 + Alembic) · Планировщик: APScheduler · Дедупликация событий по ключу
```
Технологии: Python 3.12, aiogram ≥ 3.31, httpx, Pydantic v2 + pydantic-settings, SQLAlchemy 2, Alembic, APScheduler, pytest(+asyncio). Целевой стек веба — FastAPI + HTMX (ADR 0004); база остаётся SQLite в режиме WAL (ADR 0005, это отменяет прежнюю идею «PostgreSQL в проде»).

## 8. Подводные камни (проверено на практике)

- **TMDb использует одно числовое пространство id для фильмов и сериалов.** Одно число может быть и `/movie/{id}`, и `/tv/{id}`. Поэтому нужно опрашивать оба эндпоинта; в БД ровно один тайтл на пару (источник, id). Старая запись неверного типа удаляется со всеми зависимыми строками до создания новой.
- **Внешние id в новой базе привязаны к источнику вида `tmdb_movie` / `tmdb_tv`**, а не к `tmdb`: уникальность по паре (источник, id) остаётся, и фильм с тем же числом, что у сериала, не конфликтует.
- **Даты фильма из `release_dates`:** кино — самая ранняя дата типа 3 среди всех регионов, цифровой релиз — типа 4 (тип 2 «ограниченный прокат» и 1 «премьера» не считаются). Регион владельца пока не учитывается.
- **Эпизод считается вышедшим только если `air_date` не пуст и не позже сегодня.** Эпизоды-заглушки анонсированного сезона имеют будущие даты и не должны превращать сезон в «вышедший».
- **Эндпоинт TMDb `/tv/{id}` не отдаёт список эпизодов**, только метаданные сезонов с `episode_count`. Даты эпизодов берутся пачками: `/tv/{id}?append_to_response=season/1,…` (до 20 сезонов за запрос, проверено на настоящем ответе; ответ содержит ключи `season/N`), сериал из 23 сезонов — 3 запроса.
- **TMDb `release_dates` — вложенный массив по регионам** с целочисленными типами (1 премьера, 2 ограниченный прокат, 3 прокат, 4 цифровой, 5 физический, 6 ТВ) и ключом `release_date`.
- **aiogram 3.x:** у `Message` нет `reply_text`, только `.answer()`; `InlineKeyboardMarkup(inline_keyboard=...)` требует список рядов `list[list[InlineKeyboardButton]]` (плоский список даёт `ValidationError`); проверка `event_from_user` доступна уже в middleware уровня `dp.update`; `start_polling` просит у Telegram только те типы апдейтов, на которые есть обработчики, поэтому inline-запросы боту больше не приходят.
- **SQLite:** метки времени хранятся как naive-UTC.
- **Shikimori:** один `franchise` объединяет кроссоверы, спешлы, OVA и фильмы, поэтому фильтр по названию даёт приближённый результат. Связи между тайтлами есть: `relationKind` (sequel, prequel, summary и т. д.) лежит не на `Anime`, а внутри `related { relationKind relationText anime { id kind } }`. Прежний агент искал поле на `Anime` и решил, что его нет.
- **Shikimori, цепочка сиквелов:** запрос `animes(franchise:)` не годится как основа: у части записей франшиза пуста (фильм «Созданный в Бездне: Тайна пробуждения. Часть 2» — `franchise: null`) и он тянет кроссоверы. Цепочку надёжно даёт обход по id: запрос `animes(ids:)` с `related { relationKind anime { id kind } }` и переход только по `prequel` / `sequel`. «Part N» ищется в оригинальном названии: у «Магическая битва: Смертельная миграция. Часть 2» русское название говорит «Часть 2», а оригинальное (`Kouhen`) — нет, и это сезон 4. У идущего аниме `episodes: 0` (число серий неизвестно), вышедшие считаются по `episodesAired`; `nextEpisodeAt` приходит со смещением (`+03:00`), в базе хранится UTC.
- **AniList, id по MAL-id:** запрос из нескольких `Media(idMal: …)` под разными именами целиком отвечает 404, если хоть один MAL-id AniList неизвестен. Нужна выборка `Page { media(idMal_in: […]) }`: неизвестные id просто отсутствуют.
- **AniList, расписание:** запись `Media` даёт `status` (`RELEASING`, `FINISHED`, `NOT_YET_RELEASED`), `episodes` (у идущей может быть null) и `nextAiringEpisode { episode airingAt }` (unix-время UTC). Номера серий у каждой записи свои, с 1, как у Shikimori. Выборка нескольких записей — `Page { media(id_in: […]) }`: неизвестный id просто отсутствует. AniList и Shikimori могут расходиться: на 24 октября 2026 у One Piece Shikimori ждёт серию 1181 25 октября, а AniList — 3 января 2027. Для расписания верим AniList, но если он промолчал, остаётся сохранённое.
- **Моменты вышедших серий аниме:** наш запрос к AniList не отдаёт список вышедших серий, поэтому их моменты мы не знаем. Дата, записанная впервые (из Shikimori или из момента проверки), больше не меняется; серия, найденная позже, чем она вышла, получает момент находки — отсюда небольшая задержка в «вышла серия», равная интервалу проверки (≤ 1 ч, когда серия близко).
- **Необъявленные имена:** `NameError` в редко выполняемых ветках находит `pyflakes` (`.venv\Scripts\python.exe -m pyflakes app tests`).
- **Скрипты вне проекта, читающие `.env`, не должны писать лог без `MaskingFormatter`** — иначе токен попадёт на экран.

## 9. Отвергнутые подходы и заброшенное

- **Плоский список `release_dates` с типом-строкой `"Digital"` и ключом `iso_release_date`** (TMDb, Phase 6). Реальная форма — вложенные регионы, целочисленные типы и `release_date`. Не возвращаться.
- **Плоский список кнопок и параметр `inline_keys=` в aiogram.** Правильно `inline_keyboard=[[btn], [btn]]`.
- **Поиск с опечатками перебором вариантов** (Phase 20: удаления, перестановки, суффиксы). Результаты стабильно нерелевантны, нечёткий поиск API не совпадает с намерением пользователя. Нужен другой подход.
- **Кинопоиск / KinoPub** (Phase 12). Поддержка не выдаёт `CLIENT_ID` и `CLIENT_SECRET` без партнёрского договора, OAuth Device Flow без них недоступен. Исследование API v1 проведено, реализации нет. Событие «KinoPub» и «Русская озвучка» убраны из плана.
- **Правила READY_TO_WATCH** (Phase 13). Ни один источник не отдаёт сведений о русской озвучке, а владелец смотрит сериал по сериям, а не дожидается конца сезона.
- **Режим «пустой белый список = разработка».** Убран: пустой список не пускает никого, бот не стартует (шаг 1 куска 0).
- **PostgreSQL в проде.** Заменено на SQLite в режиме WAL (ADR 0005) — для одного владельца достаточно, бэкап — один файл.
- **Перенос текущей БД (11 тестовых тайтлов).** Новая база без переноса (кусок 1), старая лежит в `data/archive/`.
- **Неофициальный запрос PSN с `sha256Hash`** (хеш истекает без предупреждения; при HTTP 400 в лог пишется «требуется обновить sha256Hash»). Цены PlayStation пойдут через PlatPrices (ADR 0003).
- **Тестовые отчёты об ошибке через `html.escape` по умолчанию** — гипотеза, что апостроф (`&#x27;`) вызывает `HTTP 400`, не подтвердилась (причиной был `OWNER_CHAT_ID`); экранирование теперь `quote=False`.
